## 结论（先看这段）

| 问题 | 实测答案 |
|---|---|
| **同 ctx 下谁快？** | dflash2 K=7 在**结构化内容**上快得多：**写代码 158.5 vs 105.6（+50%）**、数数字 **229.4 vs 134.6（+70%）**；**散文领先 0–12%**（68.9 vs 61.7；但冷启动首请求口径下两者相同：61.3 vs 59.3）。 |
| **那 dflash2 该当日常档吗？** | **不该。** 两条独立理由：① 开放生成时它的优势从 +50% decode 摊成 **代码墙钟只快 11%、散文只快 6%**（≈打平），且产出的是**另一份答案**；② 上下文天花板只有 **54272**，是 MTP 的 **1/3**。 |

| **裁决** | **维持 MTP d4**（163840/180224）。dflash2 只在"短上下文 + 结构化输出"这一个场景值得另开一档。 |

## 一、速度矩阵：同 ctx（32768）下的决定性对比

官方引擎、nvfp4、视觉 2048、贪心。
**样本基础**：主对比只用**两个全程无异常的独立引擎会话合并**（`hd-…` 与 `…-b`，n=6，每会话 3 次）；括号内是全距。
（同一配置跨会话有 ~1% 漂移：dflash2 代码单会话中位 159.5 / 158.4 ⇒ 故用合并值。§四/§五 的 K/KV 对照表按单会话 n=3，数字口径略窄。）

| 内容类型 | dflash2 K=7 | MTP d4 | 倍数 | 接受率（dflash2 / MTP） |
|---|---|---|---|---|
| **写代码**（扫雷，1500 tok） | **158.5**（158.0–160.3，n=6） | 105.6（105.4–105.9，n=6） | **×1.50** | 62.4% / 68.8% |
| **数数字**（1→400，400 tok） | **229.4**（226.8–231.9，n=6） | 134.6（133.7–135.4，n=6） | **×1.70** | 96.9% / 94.3% |
| **散文**（三元量化说明，400 tok） | **68.9**（会话中位；散文单臂 6 次中位 63.8） | 61.7（59.2–61.8，n=6） | **领先 0–12%** | 15.1–18.8% / 27.3–29.6% |
| 视觉探针（正确性） | `847` ✅ | `847` ✅ | — | — |

> 视觉探针那一列的 decode 是 4 token 的噪声，只当**正确性**用，不当速度用。
> 每个臂的每一轮读数在会话内**逐位重复**（接受率三次完全相同：62.4% / 96.9%），说明是确定性口径，不是抽奖。

**⇒ "谁快"完全取决于内容类型。** dflash2 的草稿是"top-16 候选 + 条件走链"，结构化内容里候选命中率高（代码 62.4%、数数字 96.9%），开放散文里只有 15–19%，于是每一轮的产出被 K=7 的轮成本吃回去。

## 二、★ 墙钟修正：+50% 的 decode 优势 ≠ +50% 快（本轮最重要的发现）

包内文档 `README.md` §4.6 有一条告诫：**`--lm-head-draft` 会让同一道题多生成约 85% token**（20 题问答 41,672 → 77,079），"t/s 高 ≠ 墙钟快"。

上面 §一的对比是 **`max_tokens` 截断**口径（两边都被截到 1500/400，token 数相等）⇒ 那个 +50% 是"产出同样多 token 要多久"，**不是**真实任务的墙钟。所以补测**自然停止**（`max_tokens 3000`，两边都没触顶）：

| 任务 | dflash2 K=7 | MTP d4 | 墙钟比 |
|---|---|---|---|
| **写代码** | **2841 token** @157.3 → **18.4 / 18.2 s** | **2065 token** @101.1 → **20.7 / 20.6 s** | dflash2 快 **11%**（不是 50%） |
| **散文** | 811 / 780 token @62.6 / 63.4 → 13.2 / 12.4 s | 824 / 824 token @61.8 → 13.6 / 13.5 s | dflash2 快 **5.9%**（12.8 vs 13.55 s）—— 但散文对前缀历史敏感（见 §一 脚注），**±10% 内不算差异** |

> 换个算法：**按整轮墙钟折算的实际吞吐** —— dflash2 **154.4 tok/s** vs MTP **99.8 tok/s**（含 TTFT）。若让 MTP 也写 2841 token，需要 ≈28.3 s。
> 口径提醒：每个臂的**散文第 1 次恒比第 2/3 次慢**（冷缓存：59–61 vs 61.8–69.2），所以散文读数必须看中位，并说明是哪一次。
**⇒ 本机的 token 通胀实测是「代码 +38%、散文 +0%」**（归档/包内的 +85% 是问答口径）。
**⇒ 对日常用途（写代码）：dflash2 的真实收益是约 11% 墙钟，代价是上下文降到 1/3。对写散文：约 6%，基本等于零收益。**

### ⚠ 但这 38% 不是"注水"——两份答案不是同一份输出

对比两份 code-long 的正文：**两者都是完整可运行的 HTML**（都以 `</html>` 收尾、都含 `<script>`），但

| | 字符数 | 特征 |
|---|---|---|
| dflash2 K=7 | **8,046** | 带计时器 + 重开按钮（`restartBtn` / `tick` / `setInterval`）|
| MTP d4 | **5,946** | 更精简：有 `endGame` 与 `newBtn` 重开，无计时器 |

**⇒ 在开放题上，dflash2 是"用更少的墙钟交付了更多实现"，不是"同样东西多花 token"。**
所以 §二的结论要按场景读：

- **固定长度/固定产物的任务**（数数字、按模板出 JSON、填空式改写）⇒ decode 就是墙钟，dflash2 的 **+50~70%** 是真的。
- **开放生成**（"写个扫雷"、写散文）⇒ 两边**产出长度与内容都不同**，只能比墙钟：代码 dflash2 只快 **11%**、散文只快 **6%**（≈打平）。
- 另一面：既然输出不同，**"dflash2 与 MTP 逐字一致"只对短答案成立**（见 §七 的质量四检），生成式长答案是**不可互换**的。

## 三、上下文天花板：把归档 §五 推翻，并解释上一轮的"32768 假天花板"

逐页（512 token/页）上探，`--host-kv-mib 2048` + `--wddm-evictable-budget` + nvfp4：

| 配置 | 最大 ctx | 边界证据 |
|---|---|---|
| dflash2 K=7，**视觉 2048** | **54272** | 54272 起；54784 失败：需 `2,188,398,336` B > 可用 `2,185,726,976` B（差 2.67 MB）|
| dflash2 K=7，**视觉 8192** | **41984** | 41984 起；43008 失败：需 `2,204,354,560` B |
| MTP d4，视觉 2048 / 8192 | **163840** ✅（生产档）| 180224 是归档读数，本轮未复测 |
| dflash2，**关掉视觉** | **未测**（视觉预算已证明是唯一变量；关掉应能换回约 12K ctx，但不影响速度 —— 见 §五/§一）| |

启动与占用对照：

| | dflash2 K=7 | MTP d4 |
|---|---|---|
| 权重载入 | 9.38 GiB | 7.39 GiB |
| runtime @32768 | 1.57 GiB | 1.17 GiB |
| 冷启动到就绪 | 5.2–6.1 s | 4.4–5.2 s |

**机制**：`--wddm-evictable-budget` 之后 runtime 额度固定为 **2,185,726,976 B（2.04 GiB）**。dflash2 权重多吃 1.99 GiB，于是"能装多少 KV"变成**和视觉预算抢同一笔额度**：视觉 2048 → 54272；视觉 8192 → 41984（少 12,288 token）。

**为什么上一轮量到 32768 就上不去**：`D:\build-pq2\dflash\d2-49152.err` 报"需 `2,317,601,024` B"，与我**视觉 8192 @49152** 的报错**逐字节相同** ⇒ 那一批用的是视觉 8192；若按视觉 2048，49152 是能起的。**"32768 是 dflash2 的墙"这个印象来自视觉预算，不是 ctx。**

## 四、dflash2 的 K 调优：K=7 是对的

同 ctx、nvfp4、视觉 2048，3 次中位：

| K | 写代码 | 数数字 | 散文 | 代码接受率 | 每轮成本 |
|---|---|---|---|---|---|
| 5 | 137.1 | 182.3 | 65.8–69.6 | 70.2% | — |
| **7** | **159.9** | **232.0** | 61.3–69.0 | 62.4% | 34.4 ms/轮 |
| 11 | 113.5 | 184.9 | **38.9** | 48.8% | — |

**⇒ K=7 在代码与数数字上碾压 K=5，散文持平；K=11 在 code（113.5）与 prose（38.9）上明显更差，count 只与 K5 相当（184.9 vs 182.3），综合仍输给 K7（229.4 / 158.5）。** 与包内"工程甜点 5/7"以及 §4.6 的"K=9 时散文掉到 62"一致（本机 K=11 掉到 38.9）。
散文单独复测（K=7×6 次 63.8 中位；K=5×4 次 65.8 中位）⇒ 散文上两者差 3%，噪声内。

## 五、KV 精度：生产档 nvfp4 是正确选择

| | 写代码 | 数数字 | 散文 | 代码接受率 | runtime@32k |
|---|---|---|---|---|---|
| **nvfp4**（生产，单会话 3 次中位）| **159.9** | 232.0 | 61.8–69.0 | **62.4%** | **1.57 GiB** |
| fp8（包内 dflash2 启动件默认，单会话 3 次中位）| 148.8 | 233.0 | 61.8 | 57.8% | 2.01 GiB |

**⇒ nvfp4 更快、更省额度（少 0.44 GiB）**，并且**输出文本会变**：同一题 fp8 答"好的，下面是一个完整的单文件扫雷游戏。直接保存为 `.html` 打开即可运行："，nvfp4 答"```html <!DOCTYPE html>…"。
⇒ **换 KV 精度等于换输出**，性能结论必须标注 KV 档（本轮全部 nvfp4，除本条对照）。

  --max-concurrency 1 --no-thinking ^

**运行期异常记录（已查明根因：外部并发进程，与 dflash2 引擎无关）**

主矩阵第一臂（dflash2 K=7，13:47:24 启动）在 **13:48:01** 出现异常：`req#8`（第 2 轮散文）`started` 后**始终没有 `done`**，随后 2 个请求连接被拒；再后面 2 个请求客户端报 `ok=True`（21.03 s / 7.21 s），但**引擎日志里没有对应记录**。

独立校验（只读复算 + 日志时间线比对）查明根因：

- **13:48:06 有另一个进程在同一端口 8086 起了 MTP d4 / ctx 163840 / 视觉 8192 引擎**。它先杀掉了我的引擎（⇒ 我那 3 个请求失败），又**接走**了我后续那 2 个请求。
- 证据：那 2 条的墙钟与 token 数与该外部引擎的日志逐条对应（其 `decode 99.1` / `59.6`、`mtp accepted` 行）；且**内容哈希不同** —— dflash2 三个臂的 code 输出 sha 均为 `261DA6418C49`，被接走那次是 `7EB31B5E2CE4`。
- ⇒ **该臂 r3 的读数全部作废**（本文件头部对比本来就未采用它；该臂只有 2 个有效 code 样本，已剔除）。
